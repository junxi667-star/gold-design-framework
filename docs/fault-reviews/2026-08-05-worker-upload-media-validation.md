## 1. 问题描述

### 1.1 问题场景

已认证 Worker 上传结果时，Master 只校验 SHA-256 完整性，保留客户端提供的文件名扩展名和 MIME 信息，再将文件写入同源的 `generated/` 公开目录。

### 1.2 具体表现

非图片字节可使用 `payload.js` 之类的文件名归档；静态服务会按扩展名设置响应类型。SHA-256 只能证明传输字节未变化，不能证明它是可安全公开的设计图片。

## 2. 根本原因分析

### 2.1 问题分析过程

1. 审查 Worker 上传链路，确认认证、租约和 SHA-256 校验均在 `TaskBroker.storeUpload()` 之前或之中完成。
2. 对比上传后的文件名、记录的 MIME 与静态服务器的扩展名映射，发现真实文件类型没有被验证。
3. 用 `Buffer.from("not-an-image")` 和 `payload.js` 构造回归用例，修复前该内容会进入归档流程。
4. 确认图片生成与上传的真实产物只需 PNG、JPEG、WebP，适合在媒体边界做白名单校验。

### 2.2 直接原因

`backend/task-broker.js` 原先信任传入的 `filename` 和 `mimeType`；`server.js` 对 `/generated/` 未限制扩展名。

### 2.3 根本原因

- 设计层面：把“传输完整性校验”和“媒体安全性校验”混为一层。
- 开发层面：上传契约未定义允许的二进制类型以及声明 MIME 与实际字节不一致时的行为。
- 测试层面：仅覆盖了成功上传，没有覆盖伪造类型和非图片内容。

## 3. 解决方案

### 3.1 根本解决方案

- 新增 `backend/media/image-type.js`，根据文件签名识别 PNG、JPEG、WebP，并规范化 JPEG MIME 别名。
- `TaskBroker.storeUpload()` 先校验真实图片类型，再比对声明 MIME；归档扩展名由识别结果决定。
- `ArkImageProvider` 对下载结果应用同一校验，避免上游非图片内容落盘。
- `server.js` 的 `/generated/` 仅服务 PNG、JPEG、WebP，`/metadata/` 仅服务 JSON。
- 新增非图片与伪造 MIME 的 Worker 上传回归测试。

### 3.2 影响范围评估

- 正常的 PNG、JPEG、WebP Worker 协议不变，JPEG 的 `image/jpg` 和 `image/pjpeg` 兼容保留。
- SVG、GIF、脚本和未声明或不一致的内容会以 415 拒绝；当前生图契约不依赖这些格式。
- 已有历史文件不会被删除，但新的公开归档不会再产生非白名单类型。

## 4. 预防措施

### 4.1 代码层面

- [x] 媒体白名单依据二进制签名，不依据文件名或 Content-Type。
- [x] 公开静态目录按用途限制允许扩展名。

### 4.2 测试层面

- [x] 覆盖非图片字节上传被拒绝。
- [x] 覆盖 PNG 声明为 WebP 时被拒绝。
- [ ] 未来增加新的图片格式时，同时补充签名、Worker 契约和静态服务白名单测试。

## 5. 经验总结

> 完整性哈希不能代替内容类型校验；任何写入同源公开目录的二进制文件都必须由服务端根据真实字节决定类型与扩展名。
